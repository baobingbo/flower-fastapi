## P1 严重（9 条）

### B-02 · P1 · CORS 默认通配 + 允许凭据，任意站点可带凭据跨域
- **不足**：默认 `cors_origins=["*"]` 且中间件固定 `allow_credentials=True`。已实测：Starlette 会回显请求方任意 Origin 并附 `Access-Control-Allow-Credentials: true`（含预检），等价于对任意站点开放带凭据跨域访问本 API。当前 Bearer token 存 localStorage 风险受控，但一旦引入 cookie 会话即为完整 CSRF/凭据外泄通道。
- **位置**：`backend/app/main.py:90-96`、`backend/app/core/config.py:31`
- **触发**：默认配置启动（未设 `FLOWER_CORS_ORIGINS`），任意第三方网页发起跨域请求。
- **方案**：默认值收紧为 `cors_origins=[]`；通配时 `allow_credentials=False`，显式白名单时才允许凭据；runtime_config 字段描述补充「填 * 将不携带凭据」。
- **验证**：`curl -i -H "Origin: http://evil.example.com" .../api/dashboard/summary` 不应回显该 Origin。
- **状态**：未修复
- **原编号**：P1-1

### B-03 · P1 · basic_auth 为空时存在 admin:admin 后门
- **不足**：`basic_auth_enabled=True` 而 `basic_auth` 列表为空时，`security.py` 回退默认 `admin:admin`，任何人可登录获完整权限（控制 worker、下发任务、改配置、重启后端）。三条常见触发路径：配置页先开开关后填凭据；只配了 auth 邮箱白名单而 basic_auth 为空；运维设 `FLOWER_BASIC_AUTH_ENABLED=true` 忘配凭据。前端 CredentialsEditor 空列表时还展示 admin:admin 占位行，误导用户以为是正常默认账号。
- **位置**：`backend/app/core/security.py:50-51`、`config.py:56-61`
- **触发**：`basic_auth_enabled=true` 且 `basic_auth` 为空。
- **方案**：空凭据列表时拒绝所有登录（记 error 日志返回 False）；`runtime_config.update()` 校验 `basic_auth_enabled` 置 True 时 `basic_auth` 必须非空，否则抛 ConfigError。
- **验证**：清空 basic_auth、开启开关后 `POST /api/auth/login {"username":"admin","password":"admin"}` 应 401。
- **状态**：未修复
- **原编号**：P1-2

### B-04 · P1 · GET /api/config 向任意登录用户明文返回全部用户凭据

### B-06 · P1 · /api/task/apply 可无限阻塞，耗尽线程池（DoS）
- **不足**：`timeout=None` 时 `result.get(timeout=None)` 无限等待，占用 run_in_executor 默认线程池（min(32, cpu+4) 线程）；revoke / pool / inspect / broker 查询等全部控制面共用该池。并发若干不带 timeout 的 `/api/task/apply?wait=true`（指向永不执行的队列）即可占满线程池，控制面整体瘫痪。前端默认传 timeout=10，属 API 契约层面漏洞（curl/脚本即可触发）。
- **位置**：`backend/app/api/routers/tasks.py:189-206`、`backend/app/services/manager.py:630-645`
- **触发**：`POST /api/task/apply?wait=true` 不传 timeout，或任务名使其永不执行。
- **方案**：路由层 `timeout: float = Query(30.0, ge=1, le=300)`；manager 层防御 `timeout = min(float(timeout or 60.0), 300.0)`。
- **验证**：不传 timeout 的 apply 请求应立即 422 或按上限返回；修复前并发 10+ 请求后控制操作卡死。
- **状态**：未修复
- **原编号**：P1-5

### B-07 · P1 · Dashboard/Monitor 页 15s 定时器永不清理，每次进入累加一个
- **不足**：两页 `onMounted` 里 `setInterval(loadDistribution, 15000)` 无句柄、无 `onBeforeUnmount` 清理（对比 TasksView/BrokerView 都正确 clearInterval）。组件卸载后定时器继续每 15s 请求 `task-distribution`（服务端遍历全部内存任务），且每次重新进入再建一个——来回切换 N 次就有 N 个并行轮询，内存 + 无效请求双重泄漏，浏览器越挂越卡。
- **位置**：`frontend/src/views/DashboardView.vue:123`、`frontend/src/views/MonitorView.vue:120`
- **触发**：进入「监控总览」或「实时监控」页后切换到其他页，反复进出持续累加。
- **方案**：保存句柄 + `onBeforeUnmount(() => clearInterval(distTimer))`，MonitorView 同理（长期可并入 app store 统一调度）。
- **验证**：离开页面后 Network 中 task-distribution 请求停止；来回切换 5 次后定时器数量不再增长。
- **状态**：未修复

### B-08 · P1 · manage.sh 停止逻辑（Windows 侧历史全杀 + MSYS 转换失效 + 孤儿进程，本次已部分修复）
- **不足**：三个同主题问题合并：
  1. **历史·全杀误伤（原 P1-7，未修复）**：按端口查不到 PID 的兜底 `taskkill /F /IM python.exe / node.exe` 会杀掉**整台机器**所有 python/node 进程（其他项目开发服务器、IDE 解释器、数据脚本）；Linux 兜底 `pkill -f "uvicorn"/"vite"`（manage.sh:98-99）同样会命中无关进程。
  2. **新·MSYS 路径转换失效（已修复）**：Git Bash 下 MSYS 把 `taskkill /F` 转成 `F:/` 导致「无效参数」静默失败（错误被 `2>/dev/null` 吞掉），停止服务从未真正停掉。
  3. **新·孤儿 worker 假占用端口（已修复）**：杀掉 `uvicorn --reload` 父进程后，multiprocessing 孤儿 worker 子进程仍继承监听 socket——netstat 有 LISTENING 但 PID 已不存在，端口「假占用」，新实例起不来或请求被旧孤儿处理。
- **位置**：`manage.sh:56-99`（`stop_services`）、`dev-restart.ps1:50-70`（正确参照实现）
- **触发**：Windows 下 `./manage.sh stop`（1 在按端口取 PID 失败时；2 在 Git Bash 环境恒发生；3 在曾以 --reload 启动后杀父进程时）。
- **方案**：
  - 已实施：Windows 分支 `export MSYS_NO_PATHCONV=1`（manage.sh:72）；去掉按进程名全杀兜底，改按命令行精确匹配 `uvicorn app.main | vite.js | multiprocessing-fork` 清理孤儿（manage.sh:85）；主路径按端口提取 PID 后 `taskkill /F /PID`。
  - 待办：Linux 分支仍以 `pkill -f` 兜底，应改为 `lsof -ti:$PORT | xargs -r kill -9`，解析失败时直接报错提示手动处理（对齐 dev-restart.ps1 的按 PID 精确杀）。
- **验证**：启动无关 `python -m http.server 8000` 与常驻 node 进程后执行 `manage.sh stop`，两者应存活；Git Bash 下 stop 后 `netstat` 无残留 LISTENING（含 multiprocessing-fork 进程）。
- **状态**：部分修复（Windows MSYS + 孤儿精确清理已修复；Linux pkill 全杀兜底待修）
- **原编号**：P1-7 + 新发现 #1、#3（2026-08-23）

### B-09 · P1 · RabbitMQ 非默认 vhost 时请求错误的 Management API

### B-10 · P1 · Windows 多进程可同绑 0.0.0.0:5555，旧实例（mock）抢占请求且无报错【新发现】
- **不足**：Windows 允许多个进程同时绑定 `0.0.0.0:5555`（SO_REUSEADDR 通配语义），旧实例（尤其 mock 模式）会抢占新实例的请求且无任何报错——实际曾导致用户重启 5 次后页面始终是演示模式。与 B-08 同域：停止不彻底（MSYS 失效/孤儿进程）叠加多绑语义，是 Windows 下「服务起不来/起错」的根因组合。

- **验证**：残留旧实例时执行 `manage.sh restart`，应自动清理且 `/api/system` uptime 与进程启动时间一致；页面不再停留在演示模式。

## 六、TaskDetailView（任务详情抽屉）

### TD1【中】copy() 失败也提示「已复制」
- **位置**：TaskDetailView L88-91。
- **不足**：① `navigator.clipboard?.writeText()` 的 Promise 未 await / 未 catch——非 HTTPS（很多内网运维环境是 http）或权限被拒时写入静默失败，用户却看到绿色「已复制」；② `navigator.clipboard` 为 undefined 时（老浏览器）同样提示成功。
- **方案**：
  ```js
  async function copy(text) {
    try {
      await navigator.clipboard.writeText(String(text))
      ElMessage.success('已复制')
    } catch {
      const ta = document.createElement('textarea')
      ta.value = String(text); document.body.appendChild(ta)
      const ok = document.execCommand('copy'); ta.remove()
      ok ? ElMessage.success('已复制') : ElMessage.error('复制失败，请手动选择复制')
    }
  }
  ```

### TD2【中】执行时间线只列时间戳，缺阶段耗时拆解
- **位置**：TaskDetailView L24-37（timeline computed）+ L163-168（el-timeline）。
- **不足**：时间线把 sent / received / started / succeeded 各自的时间戳平铺列出，但用户真正要的是「为什么慢」：received→started 是排队等待时长，started→succeeded 是执行时长——现在要拿秒表自己减。
- **方案**：相邻两阶段之间计算 delta 并作为 timeline-item 描述行显示（如 `started — 排队等待 3.2s`、`succeeded — 执行 128ms`）；排队等待超过阈值（如 5s）标橙色，一眼看出是 broker 积压还是任务本身慢。
- **收益**：详情页从「时间戳列表」变成「耗时归因工具」。

### TD4【低】「获取结果」弹框内容不可复制
- **位置**：TaskDetailView L74-86。
- **不足**：ElMessageBox.alert 里塞一段 `<pre>`（dangerouslyUseHTMLString），长结果只能在 pre 里手动选中复制。
- **方案**：MessageBox 自定义按钮：confirm 改为「复制」（调 `copy(prettyJson(res))`），cancel 为「关闭」。

## 十二、LoginView（登录）

### L1【中】redirect 参数未校验，存在开放重定向风险
- **位置**：LoginView L51。
- **不足**：`router.replace(route.query.redirect || { name: 'dashboard' })` 对 query 值零校验——router 守卫生成的 redirect 虽是内部路径（router/index.js L76），但构造 `/#/login?redirect=//evil.com` 可能把登录成功的用户导向外部站点（经典 open redirect，内网工具同样可能被钓鱼利用）。
- **方案**：
  ```js
  const r = route.query.redirect

  router.replace(safe ? { path: r } : { name: 'dashboard' })
  ```

- **方案**：前端维护连续失败计数，3 次后按钮进入 15s 倒计时禁用（文案「失败 3 次，15 秒后可重试」）；服务端 detail 信息透传保留。

- **不足**：390px 手机上侧边栏（展开 216px / 收起 64px）+ 表格 min-width 让内容区几乎不可用；唯一的媒体查询只隐藏 broker-url 与 badge，没有汉堡按钮把菜单收进 drawer。

  3. 桌面行为完全不变（该断点以上零 diff）。
- **收益**：手机/平板巡检场景可用；与 G7 的抽屉、网格断点一次做完。

### LAY2【中】详情抽屉宽度固定 + 状态不同步 URL
- **位置**：`components/DetailOverlay.vue` L10-17（size 写死 58% / 50%）+ `stores/detail.js`（只存 type / id）。
- **不足**：① 小屏 50% 宽的详情表格不可读（G7 成员）；② 排障时「把这条任务详情发给同事」只能发 task id 文本，不能发链接；刷新页面抽屉状态丢失。
- **方案**：
  1. 宽度按断点：移动端 100%，桌面保持 58% / 50%；
  2. URL 同步：openTask / openWorker 时 router.replace 到带 query.open（形如 task:uuid）的当前路由，关闭时移除该 query；路由守卫或 AppLayout 挂载时解析 query.open 恢复抽屉——实现深链分享。
- **收益**：移动端可读 + 详情可分享可刷新，排障协作效率显著提升。

### LAY3【低】顶栏无「最后更新时间」，channel.lastUpdate 未被展示
- **位置**：`layouts/AppLayout.vue` L102-117（channel badge 只显示模式与连接状态）+ `stores/app.js` L58-63（已维护 channel.lastUpdate）。
- **不足**：数据是 2s / 5s 级实时，但断网重连、WS 卡顿期间界面不会变红（connected 仍可能为 true 而数据停更 30s），用户无从感知「数据还是新的吗」。
- **方案**：badge tooltip 里加「最后更新 N 秒前」，并用 1s 定时器把超过 10s 未更新的 lastUpdate 显示为橙色「数据延迟 Ns」；这是监控台可信度的基础件。

## F-01（P0-1）告警与通知系统

**不足**：全代码库无任何告警规则、阈值判断、通知渠道实现（后端无 alert/notify/webhook 服务，前端无通知入口）。"监控"完全是被动的——worker 掉线、队列积压、任务失败率飙升只有盯页面才能发现；唯一外发通道是 Prometheus `/metrics`（需自接 Alertmanager）。缺阈值告警 + 多渠道通知 + 去重静默 + 告警历史，是监控平台从"看板"升级为"值守"的分水岭。

**方案**：
- **数据模型/API 要点**：新 `backend/app/services/alerts.py`，规则落 `flowerui.alerts.json`。
  - `AlertRule`：{id, name, scope: worker|task|queue|global, target, metric: queue_backlog|worker_offline|failure_rate|task_runtime|event_gap, op, threshold, duration_s（防抖）, severity: warning|critical, channels[], channel_config, enabled, silence_until}；`AlertEvent`：{id, rule_id, fired_at, payload, resolved_at, notified_via}
  - 评估：asyncio 协程每 10s 扫一次，数据源复用 `manager.state`/`manager.broker_queues()`（零侵入）；触发时 `hub.publish_threadsafe` 推前端
  - 渠道：`channels.py` 抽象（httpx 调 Webhook/钉钉/飞书机器人，smtplib 邮件）
  - API：`GET/POST /api/alerts/rules`、`PUT/DELETE /api/alerts/rules/{id}`、`GET /api/alerts/events?limit=`、`POST /api/alerts/test`（验证渠道连通性）
- **UI 入口**：侧边栏新增「告警」页（规则表格 + 启停开关 + 事件历史 + 新建规则表单）；头部铃铛 badge 显示未读告警数；触发时页面顶部红条提示
- **分步实施**：① 规则模型 + 评估协程 → ② 渠道抽象 + 测试通知 → ③ 规则管理 API → ④ 告警页 UI + 铃铛 → ⑤ 联调
- **工作量**：4~6 人天（规则引擎 1.5 / 渠道 1.5 / API+UI 2 / 联调 0.5~1）
- **联动**：浏览器通知部分见 F-12
- 详细设计：详见 feature-gaps.md P0-1

## F-02（P0-2）数据保留、长期趋势与历史查询

**不足**：全部内存态，进程重启即失——任务记录 LRU 上限 10 万条；趋势时间线 `deque(720)`@2s 采样 **仅保留约 24 分钟**；事件流环形历史 500 条；shelve 持久化默认关闭且无聚合/保留策略。无小时/天聚合，无法回答"昨天失败率多少""过去 7 天哪个任务最慢"，做不了同比环比、故障复盘、容量规划。

**方案**：
- **数据模型/API 要点**：引入 SQLite（stdlib 零新依赖，单文件 `.flowerui/history.db`）：
  - `timeline_agg`（每分钟一行：received/started/succeeded/failed/retried/revoked/active/queue_backlog）、`task_archive`（任务终态归档）、`worker_daily`（按天聚合）
  - 新 `services/history.py`：每 1min 归档新增终态任务 + timeline 采样点 rollup；保留策略 `history_retention_days` 默认 90（可配置，启动时 prune）
  - 查询 API：`GET /api/history/summary?from&to&granularity=1m|1h|1d`（聚合曲线）、`GET /api/history/tasks?from&to&state&taskname&offset&limit`（历史任务分页）、`GET /api/history/compare?days=7`（同比，可选）
- **UI 入口**：「实时图表」页顶部时间范围选择器（实时 / 24h / 7d / 自定义），按范围切换数据源与粒度；任务列表页增加"含历史归档"过滤模式；与 F-05 导出联动
- **分步实施**：① schema + 终态归档（先止血数据丢失，2~3 天）→ ② rollup + 保留策略 → ③ 查询 API → ④ 前端时间范围切换 + 图表适配 → ⑤ 联调 + 演示模式数据生成
- **工作量**：8~12 人天（schema+归档 2 / rollup+保留 2 / 查询 API 2 / 前端适配 2~3 / 联调 1~2）
- 详细设计：详见 feature-gaps.md P0-2

## F-03（P0-3）角色权限（RBAC）与操作审计日志

**不足**：`get_current_user` 只返回用户名字符串，**无任何角色概念**——所有能登录的用户权限完全相同（可关 worker、终止任务、改配置、删主题、重启后端）；凭据编辑器允许任何人编辑所有账号凭据；全部控制/配置类接口（`/api/worker/*`、task 控制端点、`PUT /api/config`、`POST /api/system/restart`、themes 写操作）**无操作审计记录**，出问题无法追溯。"多用户管理"目前仅等于"多组密码"。

**方案**：
- **数据模型/API 要点**：
  - `flowerui.users.json`：`User {username, role: admin|operator|readonly, created_at}`（与现有 basic_auth 凭据机制兼容）。admin=全部权限；operator=查看+任务下发/撤销/终止+worker 池/队列控制+告警规则；readonly=仅查看与导出
  - JWT payload 增加 `role`；新依赖 `require_role("operator")` 挂到 control.py 全部、tasks 下发/控制端点、config/themes 写操作、system/restart；凭据编辑：admin 可改他人，任意登录用户改自己
  - 审计：`services/audit.py` 提供 FastAPI 依赖 `audit_action`，追加写 `audit.jsonl`（时间/用户/IP/方法/路径/目标对象/结果码，轮转保留 30 天）；`GET /api/audit?limit=&user=&offset=` 仅 admin
- **UI 入口**：「系统信息」页新增「审计日志」Tab（admin 可见）；凭据编辑器增加角色列；403 时前端统一提示"权限不足"
- **分步实施**：① 角色模型 + JWT 改造 → ② 路由鉴权挂接 → ③ 审计中间件 + 查询 API → ④ UI → ⑤ 回归
- **工作量**：3~5 人天（角色+JWT 1 / 路由挂接 1 / 审计 1 / UI 1 / 回归 0.5~1）
- 详细设计：详见 feature-gaps.md P0-3

## F-04（P0-4）任务一键重试/重发

**不足**：任务详情操作区只有 获取结果/刷新/撤销/终止/中止，**没有任何"重跑"入口**。失败任务重发必须：切到「下发任务」页 → 手填任务名 → 手工把 args/kwargs 复制成 JSON 文本 → 再下发；参数含中文/嵌套时极易填错。重试是 Celery 运维最高频操作之一（失败修复重跑、数据补数、漏跑补偿）。

**方案**：
- **数据模型/API 要点**：`POST /api/task/retry/{taskid}?wait=&timeout=`（`tasks.py`）：从 `manager.state.tasks[taskid]` 取 name/args/kwargs 及原路由信息，复用 `manager.apply_task(name, args, kwargs, options, require_registered=False)` 重新投递，返回 `{"task-id": <新id>}`；mock 模式走 `mock.send_task` 同样可用；原任务已被内存淘汰时 404 并提示"超出保留上限，请手动下发"
- **UI 入口**：任务详情头部「重试」按钮（终态任务可用，SUCCESS 重试需二次确认）；任务列表操作列「重试」文字按钮；点击后自动打开新任务详情抽屉（`detail.openTask(newId)`），形成"重跑→跟踪"闭环
- **分步实施**：① API + mock 支持（0.5）→ ② 详情/列表按钮（1）→ ③ 新任务抽屉联动 + 测试（0.5）
- **工作量**：1~2 人天
- 详细设计：详见 feature-gaps.md P0-4

## F-05（P0-5）任务列表/数据导出 CSV·JSON

**不足**：前端无任何导出入口（全局搜索 csv/export 仅命中主题模板下载与"获取结果"按钮），后端无导出端点。失败任务清单、某时段任务数据要交给同事或贴进工单，只能手动截图或逐条复制。报表输出与跨系统协作（Excel、Jira/飞书表格）是日常刚需，实现成本却极低。

**方案**：
- **数据模型/API 要点**：`GET /api/tasks/export?format=csv|json&<与 /tasks/table 相同的过滤参数>&max=10000`：复用 `task_filter.iter_tasks` 过滤逻辑，csv 走流式 `StreamingResponse`（utf-8-sig 防 Excel 中文乱码），json 直接输出数组；`GET /api/workers/export?format=csv` 同理
- **UI 入口**：任务列表筛选栏右侧「导出」下拉（CSV/JSON，携带当前全部过滤条件，文件名含时间戳）；Worker 列表同样加导出按钮
- **分步实施**：① 两个导出端点（0.5~1）→ ② 前端导出按钮（0.5~1）→ ③ 远期并入 F-02：历史归档数据支持带时间范围导出
- **工作量**：1~2 人天
- 详细设计：详见 feature-gaps.md P0-5

## F-06（P1-1）国际化 i18n（中/英）

**不足**：前端无 `vue-i18n` 依赖；Element Plus 固定 zh-cn（`main.js`）、dayjs 固定 zh-cn（`utils/format.js`）；全部 11 个视图约 600+ 条文案（菜单、按钮、表头、提示、确认弹窗）硬编码中文；后端错误提示亦为中文。无法为海外/英文团队提供服务。

**方案**：
- **数据模型/API 要点**：文案抽到 `src/locales/zh-CN.json` / `en-US.json`（按页面分 key 命名空间）；Element Plus locale 与 dayjs locale 随切换动态更新；后端策略建议：API detail 用英文 code，前端按 locale 映射展示（或 Accept-Language 两层策略）
- **UI 入口**：顶栏增加语言切换（存 localStorage），默认跟随浏览器
- **分步实施**：① 文案抽取与英译（1.5）→ ② i18n 接线（0.5）→ ③ 后端文案策略（0.5~1）→ ④ 回归（0.5~1）
- **工作量**：3~4 人天
- 详细设计：详见 feature-gaps.md P1-1

## F-07（P1-2）任务依赖 DAG 可视化

**不足**：已具备**线性**调用链能力（`task_info` 返回 `children_tasks`、`parent_id/root_id` 过滤、任务详情"调用链"区块），但**没有 DAG 图形化**：chord/chain/group 产生的多分支子任务树只能以表格逐层点开，无法一眼看清整条工作流拓扑与每节点状态。链式/和弦任务是生产主流编排方式，DAG 视图是排查"链上哪一步挂了"的最快路径。

**方案**：
- **数据模型/API 要点**：`GET /api/task/dag/{taskid}`：以该任务为根，递归（限深 3 层、限节点 200）收集 root 下全部任务，返回 `{nodes:[{id,name,state,runtime}], edges:[[parent,child]]}`——数据全部来自内存 `state.tasks` 的 parent_id/root_id，无新数据源
- **UI 入口**：任务详情"调用链"区块增加「查看 DAG」按钮，用 ECharts `graph` 渲染（项目已有 echarts 依赖，零新增包）：节点按状态着色（复用 `TASK_STATE_COLOR`），点击节点打开对应任务详情抽屉，hover 显示耗时
- **分步实施**：① DAG 组装 API（0.5）→ ② 图渲染 + 交互（1.5）→ ③ 边界处理：环/超深/跨内存淘汰（1）
- **跨域**：与 UI 报告图表联动优化点联动（MonitorView 图表→任务列表跳转），UI 侧对应优化点见 ui.md M3
- **工作量**：2~3 人天
- 详细设计：详见 feature-gaps.md P1-2

## F-08（P1-3）定时任务（Beat/Crontab）管理

**不足**：Worker 详情有 scheduled Tab，仅**只读展示** worker 保留的 eta/countdown 任务；没有 beat 调度表查看（crontab 条目、上次/下次触发时间）、没有手动触发某个 beat 条目、没有定时任务运行记录。定时任务漏跑/重复执行是 Celery 常见事故，运维需要"beat 在跑什么、下次何时触发、手动补一次触发"（原版 flower 无此功能，属增强项）。

**方案**：
- **数据模型/API 要点**：`services/beat.py`：
  - result backend 为 Redis 时读取 beat 的 `celery-beat-schedule`（pickle/json 按 beat 存储格式解析）展示条目 + 上次运行时间
  - `GET /api/beat/schedule`（不可用时 503 + 原因，如"未连到 beat 的 Redis 或 beat 未启用"）
  - `POST /api/beat/trigger/{taskname}`：立即以该条目默认参数 `send_task` 补触发一次（复用 apply_task 通道）+ 触发历史
- **UI 入口**：新「定时任务」菜单页（beat 条目表格 + 状态 + 手动触发按钮 + 触发历史），或在系统信息页加 Tab；UI 提示写明约束：beat 进程独立，FlowerUI 只能"读+补触发"，改 crontab 仍需在代码/配置层
- **分步实施**：① schedule 读取/解析（1.5）→ ② 触发 + 历史（1）→ ③ UI（1.5）→ ④ 与不同 beat 存储兼容（0.5~1）
- **工作量**：3~5 人天
- 详细设计：详见 feature-gaps.md P1-3

## F-09（P1-4）OAuth2 单点登录

**不足**：原版 Flower 2.0.1 支持 OAuth2（`auth` 邮箱白名单正则 + `oauth2_key/secret/redirect_uri` + `auth_provider`，views/auth.py 实现 Google 等第三方登录）；FlowerUI 的 `config.py` 保留了全部字段但**没有任何 OAuth 路由与流程**，`runtime_config.py` 已自认 `auth`/`auth_provider` 两字段 `todo=True`（"OAuth 登录流程尚未接入"）。这是 README"功能全量对齐 Flower 2.0.1"中**唯一实质缺失项**（其余为增强）。企业内网通常需 SSO 而非手工分发密码。

**方案**：
- **数据模型/API 要点**：
  - `/api/auth/oauth/{provider}/start`（302 到授权页，provider 抽象：google/github/generic OIDC）+ `/callback`（换 token → 匹配 `auth` 邮箱白名单正则 → 签发本项目 JWT → 重定向前端 `/login?oauth=token`）
  - 复用现有 `auth_provider/oauth2_key/oauth2_secret/oauth2_redirect_uri` 配置字段，补进 `runtime_config.FIELDS` 可编辑（secret 脱敏）
  - `/api/auth/config` 返回已配置 provider 列表，登录页据此渲染
- **UI 入口**：登录页增加"使用 Google/GitHub 登录"按钮（配置了 provider 才显示）；接收 callback 参数后直接存 token 进首页
- **分步实施**：① provider 抽象 + 两路由（1）→ ② 邮箱白名单匹配与 JWT 签发（0.5）→ ③ 登录页 UI（0.5）→ ④ 联调（0.5~1）
- **工作量**：2~3 人天
- 详细设计：详见 feature-gaps.md P1-4

## F-10（P1-5）多 Broker/多集群集中监控

**不足**：`FLOWER_BROKER_URL` 是单一字符串，全部服务（事件采集、inspector、broker 队列查询、任务下发）绑定这一个 broker。无法在一个实例上同时看"生产集群 + 预发集群"或多组独立 Redis 队列；多环境/多业务线团队只能部署多个 FlowerUI 实例，告警、报表、操作审计也被割裂。

**方案**：
- **数据模型/API 要点**：
  - `Cluster {id, name, broker_url, result_backend?, enabled, weight_color}`，存 `flowerui.clusters.json`；当前 broker_url 迁移为唯一默认集群
  - `ServiceManager` 从单实例改为**集群注册表**：每集群一套 Events + Inspector + state
  - API 增加 cluster 路径段或查询参数：`GET /api/clusters`、`GET /api/clusters/{id}/workers` 等（现有路径向后兼容，不带参数=默认集群）；dashboard/summary 支持跨集群聚合视图
- **UI 入口**：顶栏集群切换下拉（含"全部"聚合视图）；侧边栏新增「集群管理」页（增删集群 + 连通性测试 ping_broker）
- **分步实施**：① manager/state 多实例化（1.5）→ ② API 透传 cluster（1.5）→ ③ 集群管理页（1.5）→ ④ 聚合视图（1）→ ⑤ 回归（1~1.5）
- **工作量**：5~8 人天
- **备注**：改动面大，建议作为独立版本迭代，不与其他 P1 混做
- 详细设计：详见 feature-gaps.md P1-5

## F-11（P1-6）外部系统集成：入站 Webhook 与 API Key

**不足**：出站方向只有 Prometheus 抓取；入站无任何 webhook 端点。外部系统（CI/CD、发布平台、告警平台、脚本）只能通过 UI 同款 JWT/Basic 调用，无轻量 API Key；外部变更事件无法在监控时间线上留痕——变更与故障对照是排障高频需求。无法把 FlowerUI 嵌入更宽的 DevOps 流水线。

**方案**：
- **数据模型/API 要点**：
  - API Key：`flowerui.apikeys.json` 存 `{name, key(随机 32B), role, expires_at, enabled}`；`get_current_user` 优先匹配 `Authorization: ApiKey xxx`；OpenAPI 文档注明两种鉴权方式
  - 入站 Webhook：`POST /api/hooks/event`（ApiKey 鉴权）：`{type: "deployment"|"annotation", title, detail, ts}` → 追加到 `state` 变更事件线并 WS 广播
- **UI 入口**：Dashboard 趋势图叠加变更竖线（hover 显示标题）；设置页管理 webhook 端点地址（供外部系统配置）；API Key 管理页（admin）
- **分步实施**：① API Key 模型 + 鉴权 + 管理页（1）→ ② webhook 端点 + 时间线标记（1）→ ③ 前端变更竖线（0.5~1）
- **工作量**：2~3 人天
- 详细设计：详见 feature-gaps.md P1-6

## F-12（P2-1）浏览器通知与移动端适配/PWA

**不足**：无 Web Notification API 调用，切 tab 后 worker 掉线/任务失败无系统级提醒；无响应式布局——11 个视图均为桌面表格布局，全项目仅 1 处 `@media` 断点（900px 时隐藏两个头部元素），手机端表格横向溢出、侧边栏无抽屉化；无 PWA/manifest/service worker。值班工程师手机巡检是常见场景。

**方案**：
- **数据模型/API 要点**：无后端新增
- **UI 入口**：
  - 浏览器通知：F-01 告警落地后，告警触发处加 `new Notification()`（需用户授权，配置页加"启用浏览器通知"开关 + 授权引导）
  - 移动端：Element Plus 表格加横向滚动容器 + 关键页（Dashboard/任务列表）640px 下卡片式布局（CSS-only）；manifest + 图标可"添加到主屏"（PWA 完整化可后置）
- **分步实施**：① 浏览器通知（0.5，依赖 F-01）→ ② 响应式关键页（1）→ ③ PWA 基础（0.5）
- **跨域**：移动端断点适配与 UI 报告重叠，本域保留（负责浏览器通知 + 整体方案），UI 侧对应优化点见 ui.md G7（小屏/移动端适配缺失）与 LAY1（移动端无断点：侧边栏恒定占宽）
- **工作量**：1~2 人天
- 详细设计：详见 feature-gaps.md P2-1

## F-13（P2-2）健康检查深度

**不足**：`GET /healthcheck` 恒返回 `{"status": "OK"}`，与 broker 连通性、事件采集线程存活完全无关（`manager.events.connected`/`last_error` 字段其实已存在）。K8s 探针/负载均衡器只能判断"进程活着"，无法判断"监控能力还在"。

**方案**：
- **数据模型/API 要点**：`GET /healthcheck?deep=1` 返回 `{status: OK|DEGRADED, events_connected, broker_reachable(缓存 10s), workers_online, uptime}`；DEGRADED 时 200 + 字段（K8s 可读）；默认无参行为不变保持兼容；`/api/system` 已暴露大部分字段，聚合即可
- **UI 入口**：无新增（面向 K8s/负载均衡器）
- **分步实施**：① deep 探针 + 10s 缓存 → ② 无参兼容性验证
- **工作量**：0.5~1 人天
- 详细设计：详见 feature-gaps.md P2-2

## F-14（P2-3）result_backend 等关键连接项界面可配

**不足**：`runtime_config.py` 明确将 result_backend/broker_api"已从字段表移除"，这两项只能靠环境变量设置。未配 result backend 的用户在 UI 里看不到入口，下发/查结果报 503 后只能靠系统页提示去改环境变量再重启。与 README"运行时配置界面（可编辑 + 自动落盘）"的宣称存在落差。

**方案**：
- **数据模型/API 要点**：把 `result_backend`、`broker_api` 加回 `FIELDS`（`editable=True, restart=True, secret=True`，celery 分组）；改动落盘 `flowerui.runtime.env`；重启后 `get_celery_app` 读取时注意 app 已实例化问题（在 `_apply_capacity` 同款钩子机制里重建 capp 或明确提示需重启 worker）；`/api/system` 的 `result_backend_configured` 联动刷新
- **UI 入口**：配置页 celery 分组（FIELDS 驱动自动渲染）
- **分步实施**：① 字段加回 + 落盘 → ② app 重建/重启提示 → ③ 系统页联动刷新
- **工作量**：0.5~1 人天
- 详细设计：详见 feature-gaps.md P2-3

## F-15（P2-4）测试体系与 CI

**不足**：`backend/tests/` 仅手工 e2e/诊断脚本（`functional_check.py`/`e2e_check.py` 依赖已启动服务，非 pytest；`smoke_control.py` 等依赖真实 Redis，不能无人值守）；**核心纯逻辑模块零单测**——search.py（搜索 DSL）、task_filter.py（过滤/排序）、state.py（状态机）、runtime_config.py（配置解析/落盘）、theme_manager.py（元数据解析）、mock.py（演示集群）全是"改坏了只能靠人点 UI 发现"；无 pytest 配置、无 CI 工作流、前端无任何测试。

**方案**：
- **数据模型/API 要点**：
  - 引入 `pytest + httpx`（TestClient），优先补高价值单测：search DSL 各语法分支、task_filter 排序/时间边界、runtime_config 的 .env 解析/行级更新/迁移逻辑、theme_manager 元数据解析（含非法输入）
  - 用 `FLOWER_MOCK=true` 起 TestClient 做接口级集成测试（mock 模式正是为零依赖测试设计的，当前没有利用）
  - 最小 CI：后端 pytest + 前端 `npm run build` 两条 job
- **UI 入口**：无（工程基建）
- **分步实施**：① pytest 基建（0.5）→ ② 单测（2~3）→ ③ mock 集成测试（1）→ ④ CI（0.5）
- **备注**：建议从第一个 P0 改动开始就小步补单测，避免越改越没底
- **工作量**：3~5 人天
- 详细设计：详见 feature-gaps.md P2-4
